# Pawvalor 阶段 1：项目骨架设计草案

状态：用户已于 2026-10-15 批准，进入阶段 1 实施计划。双元素章节明确保留的待定策略仍需在阶段 3 前锁定。

## 目标与边界

依据 `docs/design/pawvalor-v0.1-original.md`，建立可扩展、可测试的战斗与成长规则边界，为后续雷恩单英雄原型服务。

本阶段交付：Cocos 工程骨架、纯 TypeScript 核心接口、类型化配置与校验、雷恩示例配置、模块依赖说明及核心契约测试。可打开的工程不等于可玩的战斗 Demo；移动、怪物 AI、实际弹道与经验拾取属于阶段 2。三条完整路线属于后续阶段。

保留单英雄、远程自动攻击、移动中攻击、英雄武器绑定、普通三选一、Lv.3/7/11 固定进化，以及下一次升级免费激活组合等已确认规则。不得恢复伙伴系统或旧版单元素限制。

## 事实、建议与待定项

- 已核实：工作目录初始为空，未初始化 Git；本机有 Creator 3.0.0、3.8.3、3.8.6 版本目录。目录存在本身不证明编辑器可正常启动。
- 后续现状：用户已在 `client/` 创建 Creator 3.8.6 工程及内部 Git 仓库；此前通过 MCP 创建过 TestMCP 场景。编写实施计划时磁盘 `client/assets/` 为空，执行时需重新查询编辑器场景与资源，不能假设 TestMCP 仍存在。
- 官方文档将 3.8 标记为 LTS；下载页列出 3.8.8。参考：https://docs.cocos.com/creator/3.8/manual/ 和 https://www.cocos.com/creator-download 。
- 建议：阶段 1 优先使用本机 3.8.6，核实可执行文件后锁定精确版本，避免无必要升级。若启动或目标平台构建出现具体缺陷，再评估升级。
- 双元素与副机制槽位关系、完整组合前置表、数值及经验曲线仍是设计缺口；不能将“前期策划完成”理解为所有实现语义已确定。

## 架构选择

推荐纯 TypeScript 核心 + Cocos 适配层。核心不得导入 `cc`、微信 API、DOM 或 Node 专用 API。Node 仅作为开发期测试环境。依赖方向是表现层依赖核心，核心依赖配置类型及显式端口。

替代方案：全部使用 Cocos 组件，早期演示快，但规则测试容易依赖场景；完整 ECS 框架有利于复杂实体组合，但当前会增加框架与调试成本。现阶段不引入完整 ECS。

已确认目录约定：客户端工程及其代码、资源、测试和工具配置统一放在仓库根目录的 `client/` 下；仓库根目录的 `server/` 预留未来服务端开发。公共项目文档保留在根目录 `docs/`。在 Cocos Creator 中应打开 `client/`，而不是仓库根目录。

目录结构：

```text
client/                       # Cocos Creator 客户端工程根目录
  assets/scripts/core/        # 数学、实体 ID、事件、配置类型、系统接口
  assets/scripts/config/      # 类型化数据和标记为 prototype 的测试参数
  assets/scripts/cocos/       # 输入、生命周期、节点和表现适配
  assets/scenes/              # 编辑器创建并验证的最小启动场景
  tests/                      # 无 Cocos 依赖的核心测试
server/                       # 未来服务端，当前仅预留目录
docs/design/                  # 原始设计基线
docs/superpowers/specs/        # 架构设计文档
```

当前仅约定客户端与服务端的目录边界，服务端技术栈及接口协议在实际开发时设计。

初期使用类型化 TypeScript 配置表，避免 JSON 导入与转换链引入额外工具；配置类型保持可序列化，不在数据中嵌入执行函数。后续可增加 JSON 载入器而不修改规则层。

## 模块职责与数据契约

| 边界 | 输入与输出 | 依赖 |
|---|---|---|
| 单局流程 | 开始、暂停、恢复、结束 → 单局状态与事件 | 时钟、随机源、系统接口 |
| 战斗 | 移动意图、目标快照 → 攻击请求、命中与伤害结果 | 数学、配置、实体 ID |
| 成长 | 经验、选择命令 → 待选卡、构筑状态 | 合法性过滤、抽取、进化、组合接口 |
| 配置 | 配置表 → 结构及引用校验结果 | 纯类型 |
| Cocos 适配 | 引擎输入与帧更新 → 核心命令；核心事件 → 节点表现 | 核心公开接口、cc |

阶段 1 定义接口和必要的配置校验，不给交接文档中每个模块创建一个无行为的 Manager。实现随阶段 2/3 的实际用例添加。

基础契约包含可注入 RandomSource、模拟时钟、二维数值向量、实体句柄、单局状态和类型化事件。对象池句柄包含代次，避免延迟事件引用已被复用的实体。暂停不推进模拟时间；多局重置必须清理定时状态、待处理事件与订阅。

配置最少包括：

- HeroConfig：ID、绑定武器 ID、基础属性、三条路线 ID。
- WeaponConfig：攻击间隔、射程、弹道引用、基础伤害参数。
- ProjectileConfig：唯一运动类型、速度、尺寸、寿命、穿透次数和继承策略。
- TalentConfig：ID、分类、等级上限、前置、互斥标签、效果列表、抽取权重。
- RouteConfig：主路线、两种分支、终极技能及分支行为引用。
- ElementPolicy：附魔上限、主属性计数策略、副机制槽占用策略、共鸣配置引用。
- SynergyConfig：前置条件、效果引用、下一次升级激活策略。
- TriggerPolicy：来源类别、冷却、次数与衍生深度限制、同目标命中间隔。

所有测试数值集中保存并显式标注 `prototype`，不把测试参数表述为平衡结论。跨表引用、重复 ID、缺失效果、非法等级、路线分支结构均在启动战斗前校验；错误需指出配置 ID 和字段，禁止静默忽略。

## 成长与事件顺序提案

单次升级使用一个串行事务：进入升级 → 激活上一升级已排队的组合 → 根据目标等级进入固定进化或普通选卡 → 提交选择 → 重算构筑 → 检查组合并排到下一升级 → 关闭本次升级。

组合记录 eligibleAtLevel 和 activateAtLevel，另有 pending/active 集合。同一组合只激活一次；本级新满足的条件不能立即激活。Lv.11 自动进化也必须执行组合检查。已激活组合若满足另一个组合的前置，按同一规则排队，禁止当级递归连锁。

一次获得多个等级时逐级处理，等待当前选择提交后才处理下一级，防止跳过 Lv.3/7/11。普通升级先做合法性过滤，再做加权不放回抽样；固定节点不进入普通卡池、不消耗刷新。刷新总数由配置给定，原型值为每局两次。

候选不足三张不能复制卡片或提供满级无效卡：建议配置独立、始终有效的基础属性兜底奖励。其数值和上限策略需在阶段 3 前明确，不通过突破已确认天赋等级上限来兜底。

## 双元素待定规则的建议

建议供用户决定：主路线固有属性不计入“两个附魔”的数量；附魔独立于两个副机制槽；同属性附魔占一个附魔位并形成共鸣，不产生第二份重复命中触发。

这意味着雷霆主路线可以同时带火与冰附魔，总共出现三种属性来源。这是该建议的实际玩法成本，不能将其误称为“总计两种元素”。如果设计意图是总共最多两种元素，应改用主属性占位策略。

阶段 1 只定义策略模型，不把上述建议写成正式玩法默认值。验证用的策略配置必须明确标注测试用途；阶段 3 接入真实构筑前需锁定该规则。

直接攻击与衍生伤害携带根攻击 ID、来源类型和深度；默认衍生元素伤害不得再次触发元素。后续允许的例外必须显式配置，且受深度、次数与冷却共同限制。

## 验收与后续成本

阶段 1 验收：核心可以独立类型检查；示例配置通过校验；重复 ID、错误引用、缺失固定路线节点与非法策略能产生明确错误；依赖检查证明核心不依赖引擎；编辑器能够打开最小场景且无脚本编译错误。未实际运行的检查必须注明未验证。

阶段 2 先用占位图验证战场比例、移动、索敌、直线剑气、单种怪物和经验循环。完整角色序列帧属于 MVP 成本，不是骨架验收条件。正式伪 45°效果取决于斜俯视素材，不能仅靠二维正交相机产生。

阶段 3 验证固定进化不受随机影响、双元素策略、组合延迟且幂等、卡池合法性及多局清理。阶段 4 才验证三路线实际体验差异。

性能目标必须通过具体设备与负载记录确认；桌面预览不能证明微信真机 30/60 FPS。经验曲线还必须让玩家在 Boss 前有时间体验 Lv.11 的终极进化。

本设计对应的产品代码尚未实施。下一产物是阶段 1 实施计划，按计划进行骨架开发与验证。
