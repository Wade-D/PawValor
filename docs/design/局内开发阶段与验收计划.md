# 《萌爪骑士团》局内开发阶段与验收计划

版本：1.0  
日期：2026年11月12日  
用途：将局内开发规格拆成按依赖执行的工程、美术与验证任务。

## 1. 交付范围

完整交付四名可操作骑士、十二条主路线、二十四个分支终极、通用祝福与三种共享机制，以及生存、顺序房间、随机房间三类关卡。四名骑士均进入开发与内部验收；公开首发仍按剑士、弓箭手、法师执行，巴顿完整保留在内部角色选择中，不因首发名单缩减实现范围。

所有阶段均采用同一套战斗和成长规则。调试注入、固定种子和加速入口只用于测试，不进入正式玩家流程。本计划定义完成标准，不表示功能已经完成，也不承诺未经实际产能校准的日历工期。

开发顺序为：**工程与触屏基线 → 战斗公共规则 → 万剑散华完整样板 → 成长与共享机制 → 全部剑士及弓箭手 → 全部法师及巴顿 → 三类关卡 → 美术全面替换与平衡 → 真机发布验收。** 美术从第一阶段同步启动，不能等全部代码完成后再开始。

## 2. 现有工程与迁移清单

工程使用Cocos Creator 3.8.6与TypeScript。现有脚本包含纯核心、Cocos适配层、战斗原型、成长选择、状态和副效果处理、配置校验与自动化测试。保留这些分层与有效实现，不为了命名整齐先做全量重写。

| 现有能力或规则 | 开发处理 |
|---|---|
| `core`不依赖Cocos、微信、DOM或Node | 保持边界，伤害、成长、房间与状态规则在纯核心执行 |
| `GrowthCombatRun`管理战斗与成长 | 继续作为局内流程基础，逐步扩展关卡与NPC状态，不另建互相争夺暂停的控制器 |
| 60Hz固定步、每帧最多追5步、丢时统计 | 复用并纳入设备报告；切后台、暂停及重开清空累计时间 |
| 会话令牌、旧选择拒绝、原子构筑提交 | 保留，扩大覆盖NPC、分岔与结算按钮 |
| 1280×720横屏、64逻辑像素/世界单位 | 迁移为720×1280竖屏、32逻辑像素/世界单位，重新检查镜头、寻敌与碰撞尺度 |
| 12级封顶、每级5经验、3/7级固定节点、11级自动终极 | 改为15级、正式经验表、合法候选与出现保底；终极必须经选择获得 |
| 两附魔位、两副机制槽、原型免费组合 | 从正式构筑入口移除旧限制与旧配方；保留原型fixture仅作历史回归隔离 |
| 部分攻击和持续伤害保存旧伤害快照 | 改为规定时点锁定暴击结果、实际伤害时读取属性，不能只改卡面描述 |
| 五种诊断预设、雷霆剑雨专用fixture | 隔离到开发入口，不作为自然成型或角色完成的验收证据 |
| 当前场景以几何占位为主 | 保留灰盒用途，正式角色和预警按美术规格替换 |

原型文档记载的历史测试通过数量仅说明当时版本状态。本轮开发开始时重新执行检查、记录当前结果；任何新规则都需要自己的验证证据。

## 3. 任务执行约定

每个任务必须同时提交实现、配置、必要测试和可见效果；纯核心任务可用确定性测试与调试场景验收。所有数值来自配置表，界面说明从同一配置生成，禁止代码、卡面和设计表分别维护同一个倍率。

建议在现有目录内增量组织：角色与路线配置留在`config`，可独立测试的伤害、状态、抽卡和关卡逻辑留在`core`，Cocos节点、输入、动画、音效与资源加载留在`cocos`。只有出现第二个实际消费者时才抽象公共执行器；不要预建通用可视化技能编辑器。

同一阶段内可并行制作不依赖行为变更的美术。涉及碰撞尺寸、动画锚点、技能范围和预告节奏的资源，必须先通过该阶段的可玩样板，再批量扩展。

## 5. 工程检查与证据

在`client`目录执行`npm.cmd run verify`，覆盖核心类型检查、依赖边界与Node测试。Cocos适配器另外执行完整项目类型检查，并在Creator中实际加载场景，检查组件和资源引用。工具检查通过不能代替触屏、动画与真机验证。

测试集中于容易破坏规则的地方：暴击与属性时点、同一逻辑箭矢身份、状态刷新、护盾层、前置互斥、选择令牌、暂停与清理。不为每张纯数值卡重复编写同构测试；以配置校验及代表性边界覆盖。

每个阶段记录：构建与配置版本、设备或执行环境、随机种子、测试输入、预期与实际结果，以及必要截图或录像。自然试玩与直接注入构筑的测试明确分开。

首轮工程预算为：基准档以60fps运行、帧时间P95不超过20ms；中低档以30fps运行、帧时间P95不超过33.3ms；资源预载完成后的连续战斗不得出现超过100ms的反复卡顿；峰值内存不超过256MiB。以真机采样结果为依据，不能以桌面浏览器结果替代。

60分钟循环测试需要在预热后持续记录活跃实体、缓存候选、事件订阅、对象池已用量和内存趋势。每次结束一局后，局内活跃战斗实体与订阅应清零，池容量达到平台后不继续增长；发现持续增长即阻止封版，不以一次峰值回落判定无泄漏。

## 6. 优先级与工作量控制

当单人开发时间不足时，先完成当前阶段出口，再领取下一阶段任务。优先修复规则错误、输入丢失、战斗卡死、预警错位和真机性能问题，然后处理数值与装饰表现。

不能通过删除已确定路线、取消第四角色内部交付、恢复固定等级节点或自动赠送终极来缩短工作量。可以复用同一场景主题、敌人基础骨架、UI底板和技能特效组件，也可以在行为通过后再提高装饰细节。

每完成阶段2和阶段5各做一次实际工时复盘：统计核心编码、配置、动画、特效、测试与返工时间，再按剩余任务规模估算排期。四名角色的主要工作量来自二十四个分支终极及其组合边界，不应按“四张角色图”估计美术或开发成本。
